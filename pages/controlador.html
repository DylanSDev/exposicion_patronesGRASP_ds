El Patrón Controlador

Una solución GRASP para coordinar eventos del sistema de forma organizada.

😕 El Problema

¿Quién debe recibir y coordinar los eventos o peticiones del sistema, usualmente desde la interfaz de usuario (UI)? Si dejamos que la propia UI maneje esta lógica, mezclamos responsabilidades, haciendo el sistema más difícil de mantener y probar. Se rompe la separación entre presentación y lógica de negocio.

Analogía: El Recepcionista del Hospital

Llega un paciente (Evento del sistema)
▼
El Recepcionista recibe la solicitud, la registra y la deriva al área correcta.

¡El recepcionista no realiza la cirugía! Solo coordina y delega la tarea al especialista adecuado.

✨ La Solución

Según Larman, se debe asignar la responsabilidad de manejar un evento del sistema a una clase Controlador. Este actúa como un intermediario entre la UI y la lógica de negocio, recibiendo las peticiones y delegando el trabajo a las clases de dominio correspondientes.

El controlador centraliza la recepción de mensajes, asegurando que la UI permanezca simple y que la lógica resida en el dominio.

⚙️ Tipos o Variantes

Existen dos formas principales de implementar este patrón:

Controlador de Casos de Uso

Se crea una clase controladora específica para cada caso de uso del sistema. Por ejemplo, RegistrarVentaController o PagarReservaController. Esta opción favorece una alta cohesión y una separación clara entre procesos de negocio.

Controlador de Fachada

Se utiliza una única clase que representa al sistema en general o a un subsistema completo, como SistemaVentas. Es una solución más sencilla, útil en sistemas pequeños o cuando no se necesita una separación tan granular de los casos de uso.

🛠️ Ejemplos

Ejemplo Cotidiano: El Mozo en un Restaurante

En un restaurante, el mozo actúa como controlador. Recibe los pedidos de los clientes (eventos de la UI) y los comunica a la cocina (clases de dominio). El mozo no cocina ni prepara las bebidas; simplemente coordina la interacción entre el cliente y las áreas que realizan el trabajo.

Ejemplo con Código (Java)

La PantallaVenta (UI) no crea la venta directamente. En su lugar, llama a un método del ControladorVenta, que a su vez se encarga de instanciar y manipular los objetos de dominio como Venta.

Java
// 1. Interfaz de Usuario (Capa de Presentación)
public class PantallaVenta {
    private ControladorVenta controlador;

    public PantallaVenta() {
        controlador = new ControladorVenta();
    }

    // Evento que se dispara al pulsar un botón
    public void botonRegistrarVenta() {
        controlador.registrarVenta("Producto A", 2);
    }
}

// 2. Controlador (Capa de Aplicación)
public class ControladorVenta {
    public void registrarVenta(String producto, int cantidad) {
        // Delega la creación y lógica a la clase de dominio
        Venta venta = new Venta();
        venta.agregarItem(producto, cantidad);
        // ... aquí podría continuar con más lógica (totalizar, guardar, etc.)
    }
}

// 3. Clase de Dominio (Capa de Negocio)
public class Venta {
    public void agregarItem(String producto, int cantidad) {
        System.out.println("Agregado " + cantidad + " de " + producto);
    }
}

⚖️ Pros y Contras

Beneficios

  • Separación de responsabilidades: Aísla la lógica de la interfaz de usuario de la lógica de negocio, respetando el principio de bajo acoplamiento.
  • Claridad y organización: La estructura es clara: la UI solo muestra datos, el Controlador coordina y las clases de dominio resuelven.
  • Reutilización: Facilita la reutilización de la lógica de negocio, ya que no está atada a una interfaz específica.

Desventajas y Antipatrones

  • Controladores "gordos": Existe el riesgo de que el controlador acumule demasiada lógica que debería estar en el dominio. Esto se conoce como un "Controlador Inflado" (Bloated Controller).
  • Cuello de botella: Si no delega correctamente, puede convertirse en un punto central que maneja demasiadas tareas, violando la alta cohesión.
  • Solución (Remedio): Para evitar estos problemas, es fundamental aplicar otros patrones como Experto en Información para delegar la lógica de negocio a las clases que poseen los datos.

Principio Clave del Controlador:

Un controlador es el primer objeto después de la capa de presentación que recibe y coordina una operación del sistema.
