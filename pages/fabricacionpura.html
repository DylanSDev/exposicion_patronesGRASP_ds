El Patrón de Fabricación Pura

Una solución GRASP para mantener la cohesión y el bajo acoplamiento en el diseño.

😕 El Problema

El patrón se aplica para resolver a quién asignar una responsabilidad cuando ninguna entidad del dominio es la "Experta" adecuada. Si forzamos la responsabilidad en una clase de dominio, corremos el riesgo de crear clases con baja cohesión y alto acoplamiento, resultando en un software frágil y difícil de mantener.

Analogía: Los Juegos de Mesa

¿Quién crea una nueva partida?
▼
El Tablero: No puede crearse a sí mismo.
El Jugador: Su rol es jugar, no ensamblar el juego.

Asignar la creación a cualquiera de ellos sobrecargaría su propósito original.

✨ La Solución

La solución es crear una clase "artificial" o "inventada" que no representa un concepto del dominio del problema. Esta Fabricación Pura existe únicamente para resolver un problema de diseño, encapsulando una responsabilidad que no encaja en otro lugar.

Analogía: Crear la entidad "CreadorDeJuegos"

Entidad Artificial: CreadorDeJuegos
▼

Esta entidad, que no es parte del juego en sí, tiene la única responsabilidad de saber cómo configurar y crear diferentes partidas, dejando que el Tablero y los Jugadores se enfoquen en sus roles.

⚙️ Tipos o Variantes

Fabricación Pura no tiene variantes formales, ya que es un principio de diseño. Sin embargo, este concepto es la base de muchos patrones de diseño del catálogo de la "Gang of Four" (GoF), que utilizan clases artificiales para lograr un mejor diseño.

  • Patrones de Creación: Como Factory Method o Abstract Factory, que usan clases fabricadas para gestionar la creación de objetos.
  • Patrones de Comportamiento: Como Strategy, que usa clases para encapsular algoritmos intercambiables.
  • Patrones de Estructura: Como Adapter o Decorator, que usan clases artificiales para adaptar interfaces o añadir funcionalidades.

🛠️ Ejemplos

Ejemplo Cotidiano: Persistencia de Datos

Una clase de dominio como Producto no debería ser responsable de guardarse a sí misma en una base de datos. Hacerlo mezclaría la lógica de negocio con la de infraestructura. La solución es crear una Fabricación Pura: la clase ProductoRepository, cuya única responsabilidad es gestionar la persistencia de los objetos Producto.

Java
// 1. Clase de dominio, enfocada en la lógica de negocio
public class Producto {
    private String nombre;
    private double precio;

    public Producto(String nombre, double precio) {
        this.nombre = nombre;
        this.precio = precio;
    }

    // Getters y setters...
    public String getNombre() { return nombre; }
    public double getPrecio() { return precio; }
}

// 2. Fabricación Pura: Clase para gestionar la persistencia
public class ProductoRepository {
    // Su única responsabilidad es interactuar con la base de datos.
    public void guardar(Producto producto) {
        System.out.println(
            "Guardando el producto '" + producto.getNombre() + "' en la base de datos."
        );
        // Aquí iría la lógica real de SQL, JPA, etc.
    }
}

⚖️ Pros y Contras

Beneficios

  • Alta Cohesión: Asegura que cada clase tenga una única y bien definida responsabilidad, haciendo el código más fácil de entender y mantener.
  • Bajo Acoplamiento: Desacopla los objetos del dominio de los detalles de implementación. Un cambio en la base de datos no afectará a la clase `Producto`.
  • Reutilización: Las clases de Fabricación Pura son altamente reutilizables al encapsular una funcionalidad genérica.

Desventajas

  • Riesgo de Diseño Procedural: Si se abusa del patrón, se puede terminar con clases que son solo contenedores de funciones sin estado, lo que va en contra de la programación orientada a objetos.

Principio Clave de Fabricación Pura:

Crea clases artificiales para responsabilidades que no encajan en el dominio, con el fin de preservar la cohesión y el bajo acoplamiento.
